# img-vlm-extractor

이미지에서 값을 뽑는 것이 아니라, **뽑은 값을 믿어도 되는지 판정하는** 엔진입니다.
VLM 이 그럴듯한 오답을 쓰는 자리를 코드로 잡아내고, 못 믿을 것은 **어디가 왜 의심되는지와 함께** 사람에게 넘깁니다.

목표는 하나의 **표본**입니다 — 영수증·견적서·세금계산서·공문 같은 문서 이미지에서 값을 뽑아야 할 때,
**코드 · OCR · VLM 에게 각각 무엇을 맡겨야 오류를 막으면서 VLM 을 가장 잘 쓰는가** 를 실험으로 보입니다.

> 진행 중인 프로젝트입니다. 지금은 **연구 단계**이고, 실험 결과가 나온 뒤에 본 코드로 옮깁니다.

---

## 무엇을 푸는가

OCR 은 이미지를 글자로 바꾸고, VLM 은 **질문에 답합니다.** 그래서 양식이 제각각이거나 조금 지저분한
문서에서도 "합계가 어디인지" 를 지목해 읽어냅니다. 대신 새로운 실패가 생깁니다.

```
영수증에 "35,000" 이 흐릿하게 찍혔다

OCR  →  "3S,OOO"      깨져서 나온다 → 이상한 게 눈에 띈다
VLM  →  "38,000"      자신 있게 그럴듯한 숫자를 쓴다 → 눈에 띄지 않는다
```

**VLM 의 위험은 못 읽는 것이 아니라 그럴듯하게 지어내는 것입니다.**
깨진 결과는 걸러낼 수 있지만 그럴듯한 오답은 그대로 통과합니다.

## 역할을 나눈다

|  | 잘하는 것 | 실패하는 모양 | 맡기는 일 |
|---|---|---|---|
| **VLM** | 지저분한 이미지 · 양식 이해 · "어느 게 합계인가" | 그럴듯하게 **지어낸다** | 읽기, 의미 판단 |
| **OCR** | 깨끗한 글자 · **글자마다 좌표** | 깨진다 (눈에 띈다) | 근거 확인, 위치 표시 |
| **코드** | 산수 · 형식 · 대조 | 틀리지 않는다 (규칙이 맞다면) | 검산, 최종 판정 |

```
문서 이미지
  ├─ VLM      값을 읽는다
  └─ OCR      글자와 좌표를 읽는다         ★ OCR 은 지어내지 않는다
       ↓
  코드 검산    산수 · 형식(체크섬) · "VLM 이 쓴 값이 이미지 글자에 있는가"
       ↓
  판정         자동 처리  /  사람에게 → review.csv (문서 · 필드 · 사유 · 위치)
```

**모델은 읽기만 하고, 계산과 판정은 코드가 합니다.** 산수를 모델에게 맡기면 틀릴 뿐 아니라
**어디서 틀렸는지 알 수 없게 됩니다.**

### 검산의 예

| 문서 | 검산 | 무엇을 잡나 |
|---|---|---|
| 영수증 | Σ 품목가 ≈ 소계 · 소계 + 세금 ≈ 합계 | 숫자 오독 · 품목 누락 |
| 견적서 · 세금계산서 | 단가 × 수량 = 공급가액 · 공급가액 × 10% = 부가세 | 숫자 오독 |
| 공통 | 사업자등록번호 끝자리 체크섬 · 날짜 형식 | 그럴듯한 번호 · 없는 날짜 |
| 공통 | VLM 값이 OCR 토큰 중에 있는가 | **이미지에 없는 숫자 = 지어낸 값** |

★ **검산 통과는 근거가 아니라 반증 실패입니다.** 실측에서 검산을 통과한 값의 12% 가 틀렸습니다
(아래 "현재 상태"). 그래서 검산 하나에 기대지 않고 성격이 다른 장치를 겹칩니다.

## 어떻게 증명하는가

### 연구 질문

| | 질문 |
|---|---|
| RQ1 | 이미지가 지저분해질수록 OCR 과 VLM 중 누가 더 잘 읽나 — 교차점이 있나 |
| RQ2 | VLM 은 틀릴 때 어떻게 틀리나 — `null` / 깨짐 / **그럴듯한 오답** |
| RQ3 | 코드 장치(검산 · 체크섬 · OCR 대조)가 그럴듯한 오답을 몇 건 잡나 |
| RQ4 | VLM 을 **어떻게 부르면** 덜 지어내나 (아래 V0~V3) |
| RQ5 | 합치면 — 놓친 오답 0 을 지키면서 사람 검토량을 얼마나 줄이나 |

### VLM 사용 방식 비교 (RQ4)

| | 방식 |
|---|---|
| V0 | 기준 — 스키마만 주고 값을 뽑게 한다 |
| V1 | "안 보이면 `null`, 보이는 글자 그대로, 계산 금지" |
| V2 | OCR 토큰 목록을 같이 주고 **어느 토큰인지 번호로 고르게** 한다 — 글자는 OCR, 의미는 VLM |
| V3 | 핵심 필드 영역을 잘라 다시 읽히고, 두 번의 답을 대조한다 |

### 오류를 기다리지 않고 만든다

정상 이미지에서 VLM 오답은 드뭅니다 (CORD 41장에서 합계 오답 0건). 기다려서는 실험이 끝나지 않으므로:

- **열화** — 블러 · JPEG 압축 · 저해상도 · 얼룩을 단계별로 입힌다
- **가리기** — 특정 필드를 지운다. 그 칸의 정답은 "읽을 수 없음" 이므로 **숫자를 쓰면 그 자체가 지어낸 것**이다

### 지표

| | 뜻 | 목표 |
|---|---|---|
| **놓친 오답** | 자동처리됐는데 틀린 값 — 사고 | **0** |
| 오탐 | 맞는데 의심으로 넘긴 값 | 최소 |
| 의심 비율 | 사람에게 넘긴 비율 | 최소 |

같은 문서를 모든 방식에 통과시켜 **방식끼리 비교**합니다 (OCR 단독 · VLM 단독 · 조합).
표본이 작으므로 비율은 항상 건수와 함께 적습니다 — `12.0% (12/100)`.

## 쓰지 않는 것

| | 이유 |
|---|---|
| 벡터DB · 임베딩 | 한 장에서 정해진 값을 뽑는 것은 **검색이 아니라 추출**입니다 |
| LLM 에게 산수 | 코드가 정확하고 검증 가능합니다 |
| LLM 에게 최종 판정 | 판정까지 모델이면 무엇을 믿을지 알 수 없습니다 |

검색이 필요한 요구사항이 생기면 그때 Retrieval 계층을 따로 얹는 것이 맞다고 봅니다.
RAG 는 별도 저장소([md-rag-chatbot](https://github.com/songwookun/md-rag-chatbot))에서 다뤘습니다.

## 현재 상태

**연구 단계.** 아래는 실측으로 확인한 것만 적었습니다.

| | 결과 | 확인일 |
|---|---|---|
| 이미지 입력 + 스키마 강제 출력 | 동작 확인 | 2026-09-06 |
| VLM | `qwen/qwen3.8-27b` (Groq) — 오픈소스 가중치 | 2026-09-06 |
| 합계 검산 규칙 | 정답 라벨에서 **131/131 성립** (분기 5개) | 2026-09-07 |
| VLM 기준선 (CORD 41장) | 합계 **100%** · 품목명 **61%** — 이름-금액 짝에서 무너진다 | 2026-09-07 |
| 검산의 한계 | 검산 통과분 중 **3/25 가 오답** — 검산만으로는 부족 | 2026-09-07 |
| 같은 계열 두 모델 대조 | 합계 불일치 **0/41** — 같은 계열은 교차검증 짝이 못 된다 | 2026-09-07 |
| 로컬 OCR | `tesseract 5.5.2` (`kor` · `eng`) | 2026-10-03 |
| 비용 | **0원** — 무료 티어와 로컬 도구만 씁니다 | 2026-09-07 |

### 무료 한도가 실험 설계를 정했습니다

| | 실측 한도 | 실질 처리량 |
|---|---|---|
| Groq `qwen3.8-27b` | 하루 토큰 **200,000** (429 응답 본문에만 표기) | **하루 약 90장** |
| Gemini `2.5-flash` | 하루 **20 요청** | 실험 규모로는 부족 |

처음 설계는 **서로 다른 벤더의 두 VLM 을 대조**하는 것이었습니다. Gemini 무료 한도로는 그 규모를
돌릴 수 없어, 두 번째 신호를 **OCR** 로 바꿨습니다. OCR 은 로컬에서 무제한으로 돌고,
무엇보다 **지어내지 않습니다** — 다른 VLM 보다 독립적인 신호입니다.
실험은 하루 90장 안에서 하루에 결론 하나씩 나오도록 나눴습니다.

## 실행

```bash
brew install tesseract tesseract-lang   # 로컬 OCR (한국어 포함)

cd backend
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
cp .env.example .env      # 키를 채웁니다
```

| 키 | 무료 티어 | 발급 | |
|---|---|---|---|
| `GROQ_API_KEY` | 있음 | https://console.groq.com/keys | 필수 |
| `GEMINI_API_KEY` | 있음 | https://aistudio.google.com/apikey | 선택 |

실험 노트북을 돌리려면 `pip install -e ".[dev,lab]"` 입니다.

## 데이터

### 실물 — CORD

실물 영수증 대조군으로 **CORD** 를 씁니다. 정답 라벨과 **글자별 좌표**가 있고,
**라이선스가 원본에 명시**돼 있으며, 품목이 있어 합계 검산까지 잴 수 있습니다.

> **CORD: A Consolidated Receipt Dataset for Post-OCR Parsing**
> Seunghyun Park, Seung Shin, Bado Lee, Junyeop Lee, Jaeheung Surh, Minjoon Seo, Hwalsuk Lee
> (NAVER CLOVA) · Document Intelligence Workshop at NeurIPS, 2019
> 원본 <https://github.com/clovaai/cord> · 배포 <https://huggingface.co/datasets/naver-clova-ix/cord-v2>
> 라이선스 **[CC BY 4.0](https://creativecommons.org/licenses/by/4.0/)**
>
> *변경 사항:* 이 저장소는 원본 이미지·라벨을 **포함하지 않습니다.** 실행 시 내려받아
> 평가에 필요한 필드만 발췌하고, 비교를 위해 값을 정규화합니다(금액→숫자, 날짜→ISO).
> 열화·가리기 실험에서는 내려받은 이미지를 변형해 씁니다.

### 합성 — 견적서 · 세금계산서 · 공문

기업 문서는 **직접 만듭니다.** 값을 먼저 정하고 문서 이미지를 그리므로
**모든 필드의 정답 값과 위치를 처음부터 압니다.** 실제 회사·사람·사업자번호를 쓰지 않으며,
이미지는 저장소에 넣지 않고 코드로 다시 만듭니다.

★ 정답은 **채점에만** 씁니다. 판정 코드는 정답을 볼 수 없게 나눕니다 — 판정이 정답을 보면
실험 결과는 완벽해지고 실무에서는 쓸 수 없게 됩니다.

합성 문서만으로 결론을 내면 *"내가 만든 문서에서만 되는 방법"* 일 수 있어서 CORD 를 같이 씁니다.
